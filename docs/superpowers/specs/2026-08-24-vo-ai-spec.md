## 1. What VO-AI is

A decision-support web application for **Variation Order (VO) management** on construction
projects. Three roles collaborate on one shared VO register:

| Role | Does |
|---|---|
| **Contractor QS** | Uploads the site instruction, drawings and measurement; submits the VO |
| **Consultant QS** | Creates the project, uploads contract + BQ, cross-checks rates, assesses cost and time impact, approves or rejects |
| **Client / Developer** | Reviews the consultant's recommendation, certifies the final price, tracks all VOs |

VO-AI **assists** — every AI output is decision support and must be reviewed by the
responsible professional before approval. This is stated in the proposal and must appear
in the UI on every screen that shows a generated result.

## 3. The data model (from `template.xlsx`)

One VO register, three views. Columns marked ● are **editable by that role only**
(the spreadsheet's "yellow" rule); ○ means visible but read-only.

| Column | Contractor | Consultant | Client |
|---|---|---|---|
| VO No. | auto | ○ | ○ |
| Description | ● | ○ | ○ |
| Date VO issued | ● | ○ | ○ |
| Type of instruction (AI / EI) | ● | ○ | ○ |
| Instruction No. | ● | ○ | ○ |
| Revised drawing | ● | ○ | ○ |
| Old drawing | ● | ○ | ○ |
| Contractor's measurement (qty, rate) | ● | ○ | ○ |
| Supporting document | ● | ○ | ○ |
| VO due date | ○ | ● | ○ |
| Consultant's assessment (qty, rate, note) | ○ | ● | ○ |
| Cost impact | derived | derived | ○ |
| Time impact | ○ | ● | ○ |
| Evaluate status | ○ | ● | ○ |
| Certified status | ○ | ○ | ● |
| Final price | ○ | ○ | ● |
| Remark | ● (own) | ● (own) | ● (own) |

**Privacy rules, verbatim from the template:**
- "each role can only edit the yellow things"
- "consultant can read the document uploaded by the contractor"
- "client can read all the things in this project"
- "Each sheet need to mention what project at the above"

**Gating rules (derived from the flow):**
- Contractor may edit only while `evaluateStatus` is `Draft`, `Pending` or `Rejected`.
- Consultant may assess only once `submitted === true`.
- Client may certify only once `evaluateStatus === "Approved"`.

## 4. The consultant's core check (the differentiator)

Verbatim from `template.xlsx`, consultant sheet:

> "Cross check with contract BQ"
> "uploaded bq rate cross check with the contractor's measurement rate"
> "ensure they use the same rate with the contract bq"
> "show similar rate / different rate, if different state which rate wrong"

**Requirement:** for every measurement row the system compares the contractor's claimed
rate against the linked contract BQ rate and returns one of three states:

| State | Condition | Output |
|---|---|---|
| `same` | claimed rate == BQ rate (±0.005) | "Matches contract BQ item {code} at RM x per {unit}." |
| `different` | claimed rate != BQ rate | "Contractor claimed RM x but contract BQ item {code} is RM y. The contract BQ rate governs — the contractor's rate is overstated/understated by RM z (n%)." |
| `star` | no linked BQ item | "No matching contract BQ item. This is a star rate and must be agreed separately before certification." |

This is the single most defensible "intelligence" in the product: it is a real QS control,
it is fully deterministic, and it is auditable.

## 5. AI scope — and an honest boundary

The competition is an **AI agent** challenge, so the AI story matters. But the app must
ship as a static site (see §6), and a static page cannot hold an LLM API key without
exposing it publicly. Therefore:

**In scope for the submitted build — a deterministic rule-based analysis engine, in JS:**

1. **Variation detection** — classify a change from its description and measurement
   (material/specification change, additional work, omission, quantity variation, design
   revision) and name the affected work section.
2. **Contract clause analysis** — match the classification against a bundled clause
   knowledge base (PAM 2018 / PWD 203A variation clauses) and return the governing clause,
   what it entitles, and what the contractor must prove.
3. **Cost impact estimation** — measured totals, contractor vs assessed variance, and the
   BQ rate cross-check of §4.
4. **Time impact** — surfaced from the consultant's entry and rolled up per project.
5. **Draft VO report generation** — assembles §1–4 into a printable report.

**Explicitly out of scope for this build (and stated as such in the proposal):**
- Live LLM inference, document OCR, and drawing comparison. Uploaded files are recorded by
  name, size and uploader — their contents are not parsed.

**Honesty rule (non-negotiable):** the UI must not display invented confidence percentages
or clause numbers. Every number shown must be computed from data the user actually entered.
The existing hardcoded "94% confidence" and "Clause 13.1" must be removed or made real.

**Proposal §2.2 must describe this accurately** — a rule-based agent workflow with a
bundled clause knowledge base, with the LLM integration named as the Version 2 roadmap.

## 6. Platform constraints

| Constraint | Value |
|---|---|
| Hosting | GitHub Pages from `serenawong34-rgb/Project`, so the proposal §3.1 can give a public link |
| Backend | **None.** Static files only |
| Persistence | `localStorage`, one key: `voai.db.v1` |
| Dependencies | **Zero.** No npm packages, no CDN scripts, no build step |
| Language | Vanilla HTML / CSS / ES2020 JS |
| Tests | `node --test` (Node's built-in runner — no devDependencies) |
| Browser support | Current Chrome / Edge |
| Currency | Malaysian Ringgit, `en-MY`, two decimals, "RM " prefix |
| Login | Name + role picker only. **No passwords** — it is a demo, and storing credentials in localStorage would be dishonest security theatre |
| Blocking dialogs | No `alert()` / `confirm()` in shipped code — use inline toasts |

## 7. Demo scenario (drives seed data and proposal §3.2)

Project **"Cadangan Pembangunan ABC Residence"**, contract ABC/2026/014, sum RM 12,500,000.

- **VO-001** — ceramic → marble floor finish. Fully worked through to certified. Exercises
  all three rate states: `same` (omit ceramic at BQ rate), `star` (new marble rate),
  `different` (skirting claimed at RM 31 against BQ RM 22 — consultant corrects it).
  This is the proposal's headline example.
- **VO-002** — additional external drainage. Submitted, awaiting consultant assessment.
  This is the one the demo drives live.
- **VO-003** — ceiling revision. Contractor draft, not yet submitted.

Three demo users: Ong Wei Han (contractor), Serena Wong (consultant), Tan Zi Qian (client).

## 8. Out of scope

Real authentication; multi-user sync; file content storage; email/notifications; mobile app;
Chinese localisation; anything requiring a server.

## 9. Definition of done

- [ ] All five stages walkable end-to-end in a browser with no console errors
- [ ] Every role's edit permissions enforced, with a visible reason when a field is locked
- [ ] Rate cross-check produces all three states on the seeded data
- [ ] A VO report prints cleanly to PDF
- [ ] `node --test` passes
- [ ] Deployed to GitHub Pages and the link works in a private window
- [ ] No fabricated numbers anywhere in the UI
