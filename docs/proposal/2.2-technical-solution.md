# 2.2 Technical Solution

## 2.2.1 Development approach

VO-AI is **independently developed**. It is not built on Coze, Dify or any other agent
platform. The entire system is a static web application written in HTML, CSS and
JavaScript, with no server, no database engine and no third-party libraries.

This was a deliberate decision, taken for three reasons:

1. **The variation order calculations must be auditable.** A quantity surveyor has to be
   able to trace every figure in a VO report back to the measurement and the contract rate
   it came from. A deterministic calculation engine gives the same answer every time and
   can be inspected line by line; a probabilistic one cannot.
2. **The system must be immediately accessible.** Anyone can open the link and use the
   product straight away, with no account, no installation and no waiting for a server.
3. **Data privacy.** Contract documents, priced Bills of Quantities and variation records
   are commercially sensitive. In VO-AI, project data never leaves the user's own browser.
   Nothing is transmitted to any server, which directly addresses the data-protection
   concern raised in Section 1.2 of this proposal.

### Technology stack

| Layer | Implementation |
|---|---|
| Frontend | HTML5, CSS3, vanilla JavaScript (ES2020). No framework, no build step. |
| Backend | None. The application is entirely client-side. |
| Data storage | Browser `localStorage`, single namespaced key (`voai.db.v1`). |
| Knowledge base | Structured JavaScript object table (`js/clauses.js`), version-controlled with the source code. |
| External APIs | None. The application makes no network requests after the page loads. |
| Dependencies | Zero. No npm packages, no CDN scripts, no external fonts or images. |
| Testing | Node.js built-in test runner — **96 automated tests**, all passing. |
| Deployment | Static hosting (GitHub Pages) from the project repository. |
| Source code | `github.com/serenawong34-rgb/Project` |

The application is organised into twelve JavaScript modules with a single responsibility
each: five carry the domain logic (`calc.js`, `permissions.js`, `clauses.js`,
`analysis.js`, `store.js`), one provides shared interface components (`ui.js`), and six
drive the individual screens. Each domain module is independently unit-tested.

## 2.2.2 Overall process — from user input to result

When a contractor submits a variation order, the information passes through a fixed
seven-stage pipeline. Each stage is a named function that can be tested in isolation.

```
User input
   │  role, project, variation description, type of instruction,
   │  measurement rows (quantity + rate), supporting documents
   ▼
1. CAPTURE AND VALIDATE            store.js
   Records the submission against the project, enforces the role's
   edit rights, and writes an audit entry naming who changed what.
   ▼
2. CLASSIFY THE VARIATION          analysis.js -> classifyVariation()
   Determines the nature of the change from its description and the
   shape of its measurement (see 2.2.4).
   ▼
3. RETRIEVE THE GOVERNING CLAUSE   clauses.js -> matchClause()
   Looks the classification up in the contract clause knowledge base
   and returns the governing clause, the entitlement it creates, and
   the evidence the contractor must produce.
   ▼
4. CROSS-CHECK EVERY RATE          analysis.js -> checkRate()
   Compares each claimed rate against the priced contract BQ item it
   is linked to. This is the core professional control (see 2.2.3).
   ▼
5. QUANTIFY THE IMPACT             calc.js
   Computes the contractor's claimed total, the consultant's assessed
   total, the variance between them, and the time impact.
   ▼
6. GENERATE FINDINGS               analysis.js -> analyse()
   Produces plain-language findings for the consultant — which rates
   require correction, which require a star rate agreement, and how
   far the assessment departs from the claim.
   ▼
7. ASSEMBLE THE DRAFT REPORT       page-report.js -> renderReport()
   Compiles stages 2-6 into a printable eight-section draft VO report
   with signature blocks for all three parties.
   ▼
Output: draft VO report for professional review
```

Every value that appears in the output is derived from data the user entered or from the
clause knowledge base. **The system does not generate, estimate or infer any number that
cannot be traced to its source.**

## 2.2.3 The contract-BQ rate cross-check

This is the function that distinguishes VO-AI from a general project dashboard, and it
implements a control that quantity surveyors perform manually today.

For every measured item in a variation, the system compares the rate the contractor has
claimed against the rate for the same item in the priced contract Bills of Quantities, and
returns one of three verdicts:

| Verdict | Condition | System output |
|---|---|---|
| **Same rate** | Claimed rate equals the contract BQ rate (tolerance ±RM 0.005) | Confirms the item is valued at the contract rate and names the BQ item reference. |
| **Different rate** | Claimed rate differs from the contract BQ rate | States that the contract BQ rate governs, identifies whether the claimed rate is overstated or understated, and quantifies the difference in ringgit and percentage. |
| **Star rate** | No comparable contract BQ item exists | Flags the item as a star rate requiring separate agreement, supported by a quotation or rate build-up, before certification. |

**Worked example** (the demonstration case in Section 3.2). A client instructs a change of
living-area floor finish from ceramic tile to marble. The contractor submits three measured
items, and the system returns a different verdict for each:

| Item | Claimed | Contract BQ | Verdict |
|---|---|---|---|
| Omit ceramic floor tiles, 320 m² | RM 85.00/m² | RM 85.00/m² (item B/4.1) | **Same rate** — valued at the contract rate |
| Add marble floor tiles, 320 m² | RM 265.00/m² | No comparable item | **Star rate** — must be agreed separately |
| Skirting to match, 168 m | RM 31.00/m | RM 22.00/m (item B/4.2) | **Different rate** — contract BQ rate governs; claimed rate overstated by RM 9.00 (40.9%) |

The contractor's claim totals RM 62,808.00. After the consultant applies the contract rate
to the skirting and agrees a star rate of RM 248.00/m² for the marble, the assessed value is
RM 55,856.00 — a reduction of RM 6,952.00 that the system identified and evidenced
automatically.

The verdict always compares the **contractor's claimed** rate against the contract, not the
consultant's assessed rate. This is deliberate: the check exists to evaluate the claim as
submitted. Comparing the consultant's own correction against the contract would make the
result self-confirming and destroy its value as a check.

## 2.2.4 Interaction design: role settings, task gating and exception handling

**Role settings.** The system defines three roles — Contractor QS, Consultant QS, and
Client/Developer — implemented as a single permission matrix (`js/permissions.js`) that
maps every column of the variation register to exactly one owning role. This implements
the access rules set out in Section 1.2: each role may edit only its own columns, the
consultant may read everything the contractor uploads, and the client may read the whole
project.

Columns a user owns are highlighted; columns owned by another role are displayed read-only.
The permission matrix is defined in one place and is covered by dedicated unit tests,
because a defect that allowed one party to alter another party's contractual data would be
more damaging than a system failure — it would not be visible.

**Task gating.** Editing rights also depend on where the variation has reached in the
approval workflow:

| Stage | Contractor | Consultant | Client |
|---|---|---|---|
| Draft | May edit and submit | Locked — awaiting submission | Locked |
| Pending / Under review | May still revise | May assess, approve or reject | Locked — awaiting approval |
| Approved | Locked — assessment complete | May amend the assessment | May certify and set the final price |
| Rejected | Reopened for revision | May reassess on resubmission | Locked |

**Exception prompts.** When a field is locked, the system does not simply disable it — it
displays the reason ("Locked — waiting for the contractor to submit the VO"), so a user is
never blocked without an explanation. Validation messages appear as non-blocking notifications.
Where the system cannot classify a change, it says so and asks for a clearer description
rather than returning a guess.

**Output format.** Assessment findings are returned as discrete, plain-language statements
naming the specific rows affected and the action required. The draft report follows a fixed
eight-section structure — instruction, classification, contractual basis, measurement and
valuation, findings, time impact, supporting documents, and status — with signature blocks
for all three parties.

**Professional review requirement.** Every screen that displays a generated result, and the
report itself, carries a standing notice that the output is decision support and that final
assessment, certification and approval must be made by the responsible construction
professional. The report is labelled a draft and is never presented as a certificate. Where a
variation has not been certified, the report shows no certified value rather than a
provisional figure, so that the document cannot be mistaken for one that has contractual force.

## 2.2.5 Knowledge base

VO-AI uses two knowledge sources.

**(a) The contract clause knowledge base** — a structured, version-controlled table in
`js/clauses.js`. Entries are drawn from the standard forms of contract used in Malaysian
construction practice: **PAM 2018** (Pertubuhan Akitek Malaysia) and **PWD 203A** (Public
Works Department). It currently holds five entries:

| Reference | Title | Applies to |
|---|---|---|
| PAM 2018 Clause 11.1 | Meaning of Variation | specification, addition, omission, design |
| PAM 2018 Clause 11.2 | Provisional and Approximate Quantities | quantity |
| PAM 2018 Clause 11.6 | Valuation of Variations | all five classifications |
| PAM 2018 Clause 23.8 | Extension of Time — Architect's Instruction | addition, design, specification |
| PWD 203A Clause 24 | Variations and Provisional Sums | all five classifications |

Each entry carries five fields: the form and clause reference; the clause title; the
classifications it applies to; the **entitlement** it creates; and the **evidence** the
contractor must produce to support a claim under it. The table is ordered most-specific
first, so a remeasurement returns Clause 11.2 rather than the general valuation clause.

*Example entry — PAM 2018 Clause 11.6, Valuation of Variations:*
> **Entitlement:** Work of similar character executed under similar conditions is valued at
> the Contract Bills rates. Where the character or conditions differ, the Contract Bills
> rates form the basis of a fair valuation. Where there is no comparable rate, a fair market
> rate is agreed as a star rate.
> **Evidence required:** The relevant priced Bills of Quantities items, and for a star rate,
> a supplier quotation or build-up showing labour, material and plant.

The clause summaries are written in plain English for use within the application. They are
not reproductions of contract text, and the system does not present them as quotations. The
governing clause is always identified by its reference so that the user can consult the
actual contract.

**(b) The project's own priced Bills of Quantities** — uploaded per project by the Consultant
QS at Stage 2 and stored as structured items (code, description, unit, rate). This is the
benchmark for the rate cross-check described in 2.2.3, and it is why the accuracy of the BQ
import is treated as critical: a mis-parsed rate would silently corrupt every subsequent
comparison. The importer therefore rejects malformed rows and header rows rather than
importing them as zero-rate items.

**Classification taxonomy.** Variations are classified into five categories plus an explicit
*unclassified* state: **specification** (material or specification change), **addition**
(additional work), **omission** (work omitted), **quantity** (remeasurement or quantity
variation), and **design** (design revision). Affected work is further identified across
seven work sections — finishes, external works and drainage, ceilings, doors and windows,
structural works, electrical services, and plumbing and sanitary.

Where a description cannot be classified with confidence, the system returns *unclassified*
and no contract clause, and tells the user to provide a clearer description. It does not
default to a plausible clause. Returning a wrong clause reference would be worse than
returning none, because a professional may rely on it.

## 2.2.6 Workflow and tool calls

The processing pipeline in 2.2.2 is implemented as a chain of pure JavaScript functions
rather than as calls to an external agent platform. No external tools, plugins or APIs are
invoked. Each stage is separately testable, and the 96 automated tests cover the permission
matrix, the rate cross-check in all three verdict states, the clause lookup, the monetary
calculations, and the report generation.

The application enforces its own workflow: a variation cannot be assessed before it is
submitted, and cannot be certified before it is approved. Every state change is recorded in
an audit trail showing the actor, the action and the timestamp.

## 2.2.7 Present limitations and Version 2

We state the current boundaries of the system explicitly rather than implying capability we
have not built.

**Not implemented in this version:**
- Uploaded documents are recorded by name, size, uploader and date. Their **contents are not
  read, parsed or analysed**. The interface says so where documents are attached.
- There is no automated comparison of drawing revisions.
- There is no user authentication. Users identify themselves by user ID and role. As the
  application holds no data outside the user's own browser, a password field would provide
  the appearance of security without the substance, and we considered that worse than none.

**Version 2 roadmap:**
1. **Large language model integration** for the tasks where natural language genuinely
   helps — classifying free-text site instructions, extracting measured items from uploaded
   documents, and drafting assessment narratives. Numerical valuation would remain in the
   deterministic engine described above. This division is deliberate: language models are
   well suited to interpreting text and poorly suited to arithmetic that must be reproducible
   and auditable.
2. **Server backend with authenticated accounts** (organisational single sign-on), enabling
   genuine multi-user collaboration on a shared project.
3. **Document parsing** to extract BQ items and measured quantities from uploaded PDF and
   spreadsheet files.
4. **Drawing revision comparison** to identify changed elements between drawing versions
   automatically.

The current version establishes the workflow, the data model, the permission structure and
the professional controls. These are the components that must be correct before automated
interpretation can safely be layered on top.
