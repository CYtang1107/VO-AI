# 2.2 Technical Solution

## 2.2.1 Development approach

VO-AI is **independently developed**. It is not built on Coze, Dify or any other agent
platform. It is a web application written in HTML, CSS and JavaScript, with a Supabase
backend (Postgres database, authentication, file storage, real-time updates and server-side
Edge Functions) and Qwen language models for reading the contract.

We built it ourselves because variation orders have three requirements that a general agent
platform does not guarantee:

1. **Every figure must be auditable — the AI never calculates money.** A quantity surveyor
   has to be able to trace every figure in a VO report back to the measurement and the
   contract rate it came from. All amounts are therefore computed by a deterministic rule
   engine that gives the same answer every time and can be inspected line by line. The
   language model only interprets questions and explains the contract; any amount it quotes
   must be one of the engine's figures, or the server refuses to show the answer.
2. **Every answer must rest on the contract.** 「问合同」 (Ask the contract) answers only from
   clauses retrieved from the project's own contract, and must cite each one. The server
   checks every citation against what was retrieved. When no clause is relevant, the system
   says so instead of answering from general knowledge.
3. **Data must be protected.** Contracts, priced Bills of Quantities and variation records
   are commercially sensitive. Access is by account, every table is protected by row-level
   security, each role may write only its own fields, and the AI API key is held on the
   server, never in the browser.

The application is organised into thirty-two JavaScript modules, each with a single
responsibility: the rule engine and knowledge bases, permissions, deadlines, BQ import and
Excel export, documents and site photos, the site map, the cloud connection, 「问合同」, and
one module per screen. Each domain module is independently unit-tested.

### VO-AI as an agent

VO-AI combines a **rule-based agent**, which does everything that must be exact, with a
**retrieval-augmented language model**, which reads the contract. Each capability is a named,
tested function rather than a claim.

| Agent capability | What VO-AI does | Where |
|---|---|---|
| **Perceive** | Reads the variation record, its measurement and the project's priced BQ. Reads an uploaded BQ file (CSV or XLSX) and works out which column holds the code, description, unit and rate. Reads the GPS position of site photos. Reads scanned contracts by OCR. | `store.js`, `bqimport.js`, `capture.js`, `import-contract` |
| **Reason** | Classifies the change; finds the comparable BQ item; cross-checks every claimed rate; suggests a revised rate from past projects; matches the governing clause; infers related elements that may need remeasuring; computes the contractual time bars. | `analysis.js`, `ratehistory.js`, `clauses.js`, `elements.js`, `deadlines.js` |
| **Consult the contract** | Retrieves the nearest clauses of the project's own contract and answers the user's question from them, framed for the user's role, citing each clause. | `ask-contract`, `askcontract.js` |
| **Act** | Flags findings on the rows concerned; proposes a BQ match; tells each role what is waiting on it and how long remains; drafts the variation order report. | `copilot.js`, the screen modules |
| **Remember** | Keeps the register, every document version, and an audit trail of who changed what and when. | `store.js`, `documents.js`, Postgres |
| **Guardrails** | Declines when it cannot classify or find a clause; refuses an AI answer with an invented citation or amount; enforces who may edit what at each stage, in the browser and again in the database; leaves every decision to the responsible professional. | `permissions.js`, `rules.mjs`, migrations |

There are four agents, one per role, sharing one knowledge base but framed differently:

| Role | What its agent does |
|---|---|
| Contractor QS | Self-check before submission: does the claim stand on the contract, and what evidence is still missing? |
| Contract Administrator (Architect / Engineer / SO) | Confirms that a valid written instruction (AI / EI / SO's instruction) orders the variation, and helps decide whether to certify the assessed value. |
| Consultant QS | Assesses the variation against the contract: the governing clause, the valuation rule, whether the rates are reasonable. |
| Client / Developer | A plain summary: why the change was made, its cost and time impact, and whether it can be certified. |

## 2.2.2 Overall process — from user input to result

A variation passes through five hands, in the order a building contract requires:

```
Contractor QS submits  →  Contract Administrator confirms the instruction
   →  Consultant QS assesses  →  Contract Administrator certifies  →  Client confirms
```

Within that, the information passes through a fixed pipeline. Each stage is a named function
that can be tested in isolation.

```
User input
   │  role, project, variation description, type of instruction,
   │  measurement rows (quantity + rate), site photos, supporting documents
   ▼
1. CAPTURE AND VALIDATE            store.js, cloud.js, database trigger
   Records the submission, enforces the role's edit rights (in the
   browser and again in the database), and writes an audit entry.
   ▼
2. CLASSIFY THE VARIATION          analysis.js -> classifyVariation()
   ▼
3. RETRIEVE THE GOVERNING CLAUSE   clauses.js -> matchClause()
   Returns the governing clause, the entitlement it creates and the
   evidence the contractor must produce.
   ▼
4. CROSS-CHECK EVERY RATE          analysis.js -> checkRate()
   The core professional control (see 2.2.3).
   ▼
5. QUANTIFY THE IMPACT             calc.js
   Claimed total, assessed total, variance, time impact.
   ▼
6. GENERATE FINDINGS               analysis.js -> analyse()
   ▼
7. ASSEMBLE THE DRAFT REPORT       page-report.js -> renderReport()
   A printable draft VO report with signature blocks for all four
   parties: contractor, contract administrator, consultant, client.
   ▼
Output: draft VO report for professional review

At any stage: 「问合同」 — a question about the contract, answered from the
retrieved clauses with the figures of stages 4-5 as the only amounts allowed.
```

Every value that appears in the output is derived from data the user entered, from the
priced BQ, or from the rule engine. **No language model generates, estimates or infers any
number in VO-AI.**

## 2.2.3 The contract-BQ rate cross-check

This is the function that distinguishes VO-AI from a general project dashboard, and it
implements a control that quantity surveyors perform manually today.

For every measured item in a variation, the system compares the rate the contractor has
claimed against the rate for the same item in the priced contract Bills of Quantities, and
returns one of three verdicts:

| Verdict | Condition | System output |
|---|---|---|
| **Same rate** | Claimed rate equals the contract BQ rate (tolerance ±RM 0.005) | Confirms the item is valued at the contract rate and names the BQ item reference. |
| **Different rate** | Claimed rate differs from the contract BQ rate | States that the contract BQ rate governs, identifies whether the claimed rate is overstated or understated, and quantifies the difference in ringgit and percentage. |
| **Star rate** | No comparable contract BQ item exists | Flags the item as a star rate requiring separate agreement, supported by a quotation or rate build-up, before certification. |

**Worked example** (the demonstration case in Section 3.2). A client instructs a change of
living-area floor finish from ceramic tile to marble. The contractor submits three measured
items, and the system returns a different verdict for each:

| Item | Claimed | Contract BQ | Verdict |
|---|---|---|---|
| Omit ceramic floor tiles, 320 m² | RM 85.00/m² | RM 85.00/m² (item B/4.1) | **Same rate** — valued at the contract rate |
| Add marble floor tiles, 320 m² | RM 265.00/m² | No comparable item | **Star rate** — must be agreed separately |
| Skirting to match, 168 m | RM 31.00/m | RM 22.00/m (item B/4.2) | **Different rate** — contract BQ rate governs; claimed rate overstated by RM 9.00 (40.9%) |

The contractor's claim totals RM 62,808.00. After the consultant applies the contract rate
to the skirting and agrees a star rate of RM 248.00/m² for the marble, the assessed value is
RM 55,856.00 — a reduction of RM 6,952.00 that the system identified and evidenced
automatically.

The verdict always compares the **contractor's claimed** rate against the contract, not the
consultant's assessed rate. This is deliberate: the check exists to evaluate the claim as
submitted. Comparing the consultant's own correction against the contract would make the
result self-confirming and destroy its value as a check.

## 2.2.4 Interaction design: role settings, task gating and exception handling

**Role settings.** The system defines four roles — Contractor QS, Contract Administrator
(Architect / Engineer / SO), Consultant QS, and Client/Developer — implemented as a single
permission matrix (`js/permissions.js`) that maps every field of a variation to exactly one
owning role. The same rules are enforced a second time in the database
(`check_vo_fields`), so they hold even for a request that bypasses the interface. A defect
that allowed one party to alter another party's contractual data would be more damaging than
a system failure — it would not be visible — so the matrix is covered by dedicated tests and
was also checked against the live database for every role.

On a variation, each role works in its own panel, containing only the fields it owns; the
other roles' panels are available read-only, so a client can still read the consultant's
assessment before confirming.

**Task gating.** Editing rights also depend on where the variation has reached:

| Stage | Contractor | Contract Administrator | Consultant | Client |
|---|---|---|---|---|
| Draft | May edit and submit | Locked — awaiting submission | Locked | Locked |
| Submitted | May still revise | May confirm the instruction or return it | Locked — awaiting the instruction | Locked |
| Instruction confirmed | May still revise | — | May assess, approve or reject | Locked |
| Approved by the consultant | Locked | May certify the assessed value | May amend the assessment | Locked — awaiting certification |
| Certified | Locked | — | — | May confirm and set the final price |
| Returned / Rejected | Reopened for revision | — | May reassess on resubmission | Locked |

**Exception prompts.** When a panel is locked, the system states the reason at the top of it
("Waiting for the contract administrator to confirm the instruction."), so a user is
never blocked without an explanation. Where the system cannot classify a change, it says so
and asks for a clearer description. Where 「问合同」 finds no relevant clause, it says so and
gives no answer; where an answer fails the server's checks twice, it is not shown and the
user is told why.

**Output format.** Findings are discrete, plain-language statements naming the rows affected
and the action required. Contract answers are short (at most six points), in the language of
the question, each point followed by its citation, e.g. 「引用：PAM 2018 第 11.6 条」 or
[Ref: PAM 2018 Clause 11.6]; the cited clause text can be opened beneath the answer. The
draft report follows a fixed ten-section structure ending with the status of all four steps
and signature blocks for all four parties.

**Professional review requirement.** Every screen that displays a generated result, and the
report itself, carries a standing notice that the output is decision support and that final
assessment, certification and approval must be made by the responsible construction
professional. The report is labelled a draft and is never presented as a certificate. Where a
variation has not been certified, the report shows no certified value.

## 2.2.5 Knowledge base

VO-AI uses three knowledge sources: two structured ones that the rule engine reads, and the
contract text itself, which 「问合同」 searches.

**(a) The contract clause knowledge base** — a structured, version-controlled table in
`js/clauses.js`. Entries are drawn from the standard forms of contract used in Malaysian
construction practice: **PAM 2018** (Pertubuhan Akitek Malaysia) and **PWD 203A** (Public
Works Department). It currently holds five entries:

| Reference | Title | Applies to |
|---|---|---|
| PAM 2018 Clause 11.1 | Meaning of Variation | specification, addition, omission, design |
| PAM 2018 Clause 11.2 | Provisional and Approximate Quantities | quantity |
| PAM 2018 Clause 11.6 | Valuation of Variations | all five classifications |
| PAM 2018 Clause 23.8 | Extension of Time — Architect's Instruction | addition, design, specification |
| PWD 203A Clause 24 | Variations and Provisional Sums | all five classifications |

Each entry carries five fields: the form and clause reference; the clause title; the
classifications it applies to; the **entitlement** it creates; and the **evidence** the
contractor must produce to support a claim under it. The table is ordered most-specific
first, so a remeasurement returns Clause 11.2 rather than the general valuation clause.

*Example entry — PAM 2018 Clause 11.6, Valuation of Variations:*
> **Entitlement:** Work of similar character executed under similar conditions is valued at
> the Contract Bills rates. Where the character or conditions differ, the Contract Bills
> rates form the basis of a fair valuation. Where there is no comparable rate, a fair market
> rate is agreed as a star rate.
> **Evidence required:** The relevant priced Bills of Quantities items, and for a star rate,
> a supplier quotation or build-up showing labour, material and plant.

The clause summaries are written in plain English for use within the application. They are
not reproductions of contract text, and the system does not present them as quotations. The
governing clause is always identified by its reference so that the user can consult the
actual contract.

**(b) The project's own priced Bills of Quantities** — uploaded per project by the Consultant
QS at Stage 2 and stored as structured items (code, description, unit, rate). This is the
benchmark for the rate cross-check described in 2.2.3, and it is why the accuracy of the BQ
import is treated as critical: a mis-parsed rate would silently corrupt every subsequent
comparison. The importer therefore rejects malformed rows and header rows rather than
importing them as zero-rate items.

**Classification taxonomy.** Variations are classified into five categories plus an explicit
*unclassified* state: **specification** (material or specification change), **addition**
(additional work), **omission** (work omitted), **quantity** (remeasurement or quantity
variation), and **design** (design revision). Affected work is further identified across
seven work sections — finishes, external works and drainage, ceilings, doors and windows,
structural works, electrical services, and plumbing and sanitary.

Where a description cannot be classified with confidence, the system returns *unclassified*
and no contract clause, and tells the user to provide a clearer description. It does not
default to a plausible clause. Returning a wrong clause reference would be worse than
returning none, because a professional may rely on it.

**(c) The contract text itself — a vector knowledge base.** The full text of PAM 2018 is
split by clause into **231 passages**, each embedded with DashScope `text-embedding-v4`
(1,024 dimensions) and stored in Postgres with `pgvector`. A question is embedded the same
way and `match_chunks` returns the nearest passages above a similarity bar of 0.35 — only
from the contract of the asker's own project. The consultant can add a further contract from
the Documents page: a text PDF is read directly, and a **scanned PDF is read by OCR**
(`qwen-vl`), then split by clause and stored; the consultant is asked to check the
imported text against the signed contract, and can open every stored clause to do so. These
passages are the only source 「问合同」 may answer from (see 2.2.6).

## 2.2.6 Workflow and tool calls

The rule-engine pipeline in 2.2.2 is a chain of pure JavaScript functions. The language
model is used in two places only, each behind an Edge Function that holds the API key:

- **`ask-contract`** — checks that the caller is a member of the project (or a guest within
  the daily limit, demo project only); embeds the question; retrieves the nearest clauses of
  that project's contract; asks Qwen to answer from those clauses only, with the rule
  engine's figures for the variation as the only amounts it may use; then checks the answer
  (citations and amounts, see 2.2.1) before returning it with the clauses it cited.
- **`import-contract`** — for the consultant only: OCR of a scanned contract page by page,
  then splitting by clause, embedding and storing it in the project's knowledge base.

The 438 automated tests cover the permission matrix (four roles, every stage), the rate
cross-check in all three verdict states, the clause lookup, the element relationships, the
deadline arithmetic, the BQ column detection, the past-rate suggestions, document versions
and site photos, the monetary calculations, the report, and the answer checks of
`ask-contract` (invented citations, unsupported amounts, missing citations).

The application enforces its own workflow: a variation cannot be assessed before its
instruction is confirmed, and cannot be confirmed by the client before the contract
administrator has certified it. Every state change is recorded in an audit trail showing the
actor, the action and the timestamp.

## 2.2.7 Present limitations and next steps

We state the current boundaries of the system explicitly rather than implying capability we
have not built.

**Not implemented in this version:**
- The contents of drawings and quotations are stored, versioned and shown, but **not
  analysed**; there is no automated comparison of drawing revisions.
- The contract knowledge base holds PAM 2018. Other standard forms (PWD 203A, CIDB) can be
  imported the same way but have not been loaded.
- The past-project rates used for revised-rate suggestions are a small sample set, not a
  market database.
- Accounts use email and password; there is no organisational single sign-on yet.
- The OCR of a scanned contract may misread words; the consultant is asked to check the
  imported text against the signed contract, and every answer reminds the reader that the clause text came from a scan.

**Next steps:**
1. Drawing revision comparison, to identify changed elements between versions.
2. Reading quantities from quotations and measured drawings into the measurement table.
3. More standard forms of contract, and a larger, dated rate database.
4. Organisational sign-on and notifications by email.
5. Field testing with contractors, consultants and clients on a live project, to measure
   time saved and errors caught.
