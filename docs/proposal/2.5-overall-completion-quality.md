## 2.5.2 What is complete

**The variation order lifecycle.** A contractor raises a variation, enters the measurement,
attaches drawings and supporting documents, and submits it. The consultant assesses it
against the contract, cross-checks every rate, records a time impact and approves or
rejects. The client certifies a value. Each step is recorded with its author and timestamp.

**The contract-BQ rate cross-check.** For every measured item the system compares the
claimed rate against the priced contract Bills of Quantities and returns one of three
verdicts — same rate, different rate (naming which rate governs and by how much the claim
departs from it), or star rate. The system finds the comparable BQ item itself, and explains
why it matched.

**Contract clause analysis.** Five clauses from the PAM 2018 and PWD 203A standard forms,
each carrying the entitlement it creates and the evidence required, matched deterministically
to one of five variation classifications and ordered most-specific-first.

**Element-based consequential measurement.** A knowledge base of 20 building elements and
their relationships, prompting the surveyor to confirm whether the elements that commonly
change together also require remeasurement.

**Contractual time bars.** The consultant's 30-day evaluation period, the 28-day period for
requesting further information, and the contractor's 28-day period to respond, each computed
automatically with overdue and approaching states surfaced on the dashboard.

**Bills of Quantities import.** A priced BQ can be uploaded as CSV or XLSX. The system
determines which column holds the code, description, unit and rate by examining the data,
explains its reasoning, previews what it will import, reports what it skipped, and allows
the user to correct any column before anything is committed.

**Role-based access.** Every column of the register belongs to exactly one role, and editing
rights follow the workflow state. Where a field is locked, the system explains why.

**Documentation and evidence.** Document revision history, a project-wide documents view,
role-specific variation order reports in the required section order, and an all-variations
summary against the contract sum. Reports print to PDF through the browser.

**Practical completeness.** Bilingual interface, usable on a phone, project export and import
for exchanging a complete project between team members, and an optional project passcode.

## 2.5.3 Engineering quality

The project was developed test-first. Each module was implemented against its tests, then
independently reviewed before being accepted, with the review report recorded. **303
automated tests** cover the permission matrix, the rate cross-check in all three verdict
states, the clause lookup, the element relationships, the deadline arithmetic, the BQ column
detection, the monetary calculations and the report generation.

Two disciplines are worth stating because they shaped the result:

**Every screen was verified in a real browser, not merely tested.** Early in development, a
defect was introduced that prevented the application from rendering at all. It passed six
consecutive code reviews, because each review confirmed that the tests passed and that every
file was served successfully — but a served file is not a parsed file, and no review had
opened a browser console. Since that was discovered, every change has been confirmed visually
in a live browser before being accepted.

**Findings were recorded rather than quietly resolved.** During development an automatic
rate-matching method was tested that would have matched a genuine star-rate item to an
unrelated contract rate — a confident wrong answer of exactly the kind this system exists to
prevent. It was rejected in favour of a measure that separates those cases with a clear
margin. The reasoning is documented rather than hidden.

## 2.5.4 Present limitations, stated plainly

We state these because a system used for contractual decisions should be honest about its
boundaries, and because a limitation named is a limitation a user can work around.

**Document contents are not read.** Uploaded drawings and supporting documents are recorded
by name, size, uploader and date. The system does not parse, store or analyse the files
themselves. The exception is the BQ import, which does read the data in a CSV or XLSX file —
the interface distinguishes the two cases.

**PDF extraction is not supported.** A priced BQ must be provided as CSV or XLSX. Extracting
tabular data reliably from PDF requires capabilities beyond what a client-side application
can honestly provide, and a silently misread rate would corrupt every subsequent comparison.

**No drawing comparison.** The system records revised and superseded drawings and their
revision history, but does not compare them to identify what changed.

**No user authentication.** Users identify themselves by user ID and role. An optional
passcode may be set on a project, but as the application holds no data outside the user's own
browser, that passcode locks the screen on that device rather than protecting the data. This
is stated in the interface where the passcode is set.

**Data is local to one browser.** There is no server, so project data does not synchronise
between devices or users. Project export and import allow a complete project to be exchanged
as a file, which serves a small team, but it is not live collaboration.

**The clause knowledge base holds five clauses.** They are the provisions most often engaged
by a variation, and they are summarised in plain English for use in the application rather
than reproduced as contract text. The clause reference is always shown so the user can
consult the contract itself.

**No field validation with real project data.** The system has been tested against a
representative worked example, not against a live construction project. The accuracy of
classification and cost assessment on real project data requires professional validation.

## 2.5.5 Future optimisation

**Version 2 — server and collaboration.** A backend with authenticated accounts and
organisational sign-on, enabling genuine multi-user collaboration, live shared state and
notification when a variation requires attention. Project export and import would be
superseded by synchronisation.

**Version 2 — language model integration.** A large language model applied where natural
language genuinely helps: classifying free-text site instructions, extracting measured items
from uploaded documents, and drafting assessment narratives. **Numerical valuation would
remain in the deterministic engine.** This division is deliberate rather than provisional:
language models interpret text well and perform reproducible auditable arithmetic poorly,
and a variation order's figures must be traceable.

**Version 3 — document intelligence.** PDF extraction of bills and measured quantities, and
automated comparison of drawing revisions to identify changed elements.

**Continuous — knowledge base expansion.** Additional contract forms, a wider element
relationship table, and measurement rules drawn from the standard methods of measurement.

**Required before industry use.** Validation of the clause references and element
relationships by a practising quantity surveyor, and usability testing with contractors,
consultants and clients on live projects.

## 2.5.6 Assessment

The system delivers a complete, working variation order workflow with a genuine professional
control at its centre, deployed and available for immediate use. Its boundaries are declared
rather than concealed, and its architecture was chosen so that every figure it displays can
be traced to the data it came from.

What remains is the work that cannot be done in a competition timeframe: validation against
real projects, professional review of the contract knowledge base, and the server
infrastructure that genuine multi-party collaboration requires. The foundation those would
build on — the workflow, the data model, the permission structure and the professional
controls — is complete and tested.
